# PRD：发票识别工具（发票箱 + 内嵌识别 + OCR 兜底 + 查验）

> 产出角色：产品经理 许清楚（Xu）
> 关联系统：mfr-cloud-finance「智慧经营」业财一体化（Vue3 前端 + FastAPI 后端 + SQLite）
> 决策基调：老板拍板方向——**一条 OCR + 宽松解析 + 查验 的管道，配一个轻量发票箱（批量收票、自动结构化、再挂到报销/采购），录入界面保留"看到新发票重新识别"的内嵌按钮。不是重造一个孤岛工具。**

---

## 1. 产品目标

把"发票进系统"从**手工敲字段**变成**上传即结构化**，并消除两类痛点：

1. **录入错误 & 慢**：发票号/税号/金额手工敲，易错且费时。
2. **图片型发票识别不出**：现有 `invoiceFields.ts` 宽松解析在 13 张真实样本中文本层 11 张精准（67/0），但 **2 张空火车票 + 1 张行程单是纯图片/二维码，必须 OCR 兜底**——这正是本工具要补的硬缺口。

设计灵魂与系统一致——**业务驱动账务**：发票结构化后反写报销/采购 → 自动生成凭证，不在中间制造割裂环节。

---

## 2. 用户故事

| # | 角色 | 故事 |
|---|------|------|
| U1 | 报销人 | 在「我的报销」(`MyReimburse.vue`) 录入时，上传发票 PDF/图片，点"重新识别"，字段自动回填，核对一眼确认。 |
| U2 | 报销人 | 把一堆差旅发票丢进「发票箱」，系统批量 OCR + 结构化，做报销时从箱子里勾选带入。 |
| U3 | 会计 | 在发票箱看到每张发票的结构化字段 + 识别置信度，人工校正后"挂接到报销单/采购单"。 |
| U4 | 老板 | 担心假票 → 对增值税类发票发起**查验**，结果标记 真/假/异常。 |
| U5 | 所有人 | 同一张发票（同发票号+税号）不重复报销——系统去重提示。 |

## 3. 需求池

### P0（本期必做）

| ID | 需求 | 说明 |
|----|------|------|
| P0-1 | **发票箱页面**（`invoice/InvoiceInbox.vue` 新增） | 列表（文件名/类型/状态/提取摘要/挂接单号）+ 拖拽上传区 + 批量识别按钮 + 状态机：待识别 → 已识别 → 已挂接。 |
| P0-2 | **OCR 管道兜底** | 图片型发票（png/jpg/扫描 PDF）走 `tesseract.js`（已引入 `invoiceParser.ts`）→ 文本 → 复用 `invoiceFields.ts` 宽松解析。补齐那 3 张图片票（2 空火车票 + 1 行程单）。 |
| P0-3 | **内嵌"重新识别"按钮** | 在 `MyReimburse.vue` / `MyPurchase.vue` 录入界面加"上传发票→识别回填"弹窗，调用同一管道。 |
| P0-4 | **发票箱后端存储** | 新增 `invoice_inbox` 表：id / 原文件名 / 文件存储路径(或 blob) / 提取字段JSON / 来源(上传/箱) / 状态 / 挂接单号 / 创建时间。与正式 `进项发票` 表分离，**确认挂接后才生成正式进项发票记录 + 反写凭证**。 |
| P0-5 | **发票 → 报销/采购 挂接** | 发票箱勾选发票 → 带入 `MyReimburse` / `MyPurchase` 明细，字段一键填充；挂接后状态置"已挂接"。 |

### P1（尽快做）

| ID | 需求 | 说明 |
|----|------|------|
| P1-1 | **查验（增值税类）** | 接税务局全国增值税发票查验平台或第三方（百望/航信/票易通），按 发票号+税号+金额+日期 验真。结果标记 真/假/异常。非增值税类（火车/机票/定额）标注"不支持查验"。 |
| P1-2 | **去重** | 同一 `发票号 + 销售方税号` 已存在于发票箱或已挂接报销 → 提示重复，阻止重复报销。 |
| P1-3 | **识别结果可编辑** | 发票箱每条提取字段可人工校正（金额/税号/名称），校正后写回 `invoice_inbox`。 |

### P2（后续）

| ID | 需求 | 说明 |
|----|------|------|
| P2-1 | **后端 OCR**（更准） | 前端 tesseract 为 P0 默认；P2 评估后端 OCR 服务（部署成本 vs 准确率）。 |
| P2-2 | **发票箱汇总/导出** | 按状态/期间统计、导出 Excel。 |
| P2-3 | **移动端拍照识别** | 微信/App 拍照 → 同管道。 |

## 4. UI 设计稿（描述，非像素稿）

│ 发票箱                         [拖拽上传区] [批量识别] │
├──────┬────────┬────────┬────────┬──────────┤
│ 文件名 │ 类型   │ 状态   │ 提取摘要        │ 操作     │
│ a.pdf │ 增值税 │ 已识别 │ 金星科技 ¥889   │ [校正][挂接]│

  金额：  〔838.68〕  税额：〔50.32〕  价税合计：〔889.00〕

## 5. 待确认问题（需老板/会计拍板）

1. **查验实现方式**：税务局官方查验平台 API 需研究可用性（签名/限频/仅增值税发票）；建议 P1 先用**轻量版**——跳官方查验页 + 记录人工查验结果标记，完整 API 对接留作 P1 末或 P2。是否同意？
2. **发票箱存储位置**：建议新增独立 `invoice_inbox` 表（与正式进项发票分离，确认挂接后才落正式表+凭证）。还是直接写入现有进项发票流程？
3. **OCR 部署端**：P0 用前端 `tesseract.js`（零部署、隐私在本地浏览器），准确率对火车/行程单这类版式够用即可；更准的后端 OCR 作 P2。是否接受前端 OCR 的准确率上限？
4. **文件留存**：上传的发票 PDF/图片原文件存后端目录（不入库二进制），还是仅存路径引用？建议存 `backend/uploads/inbox/`，DB 只存路径。
5. **与现有「进项发票」模块关系**：发票箱是"入口/暂存"，确认挂接后才生成正式进项发票 + 反写账务。确认这个边界？

---

## 6. 范围边界（明确不做）

- ❌ 不为每种票面写专属解析器（死板，老板已否）。一律走 `invoiceFields.ts` 宽松解析。
- ❌ 不接 XML 发票（老板既定：只要 PDF）。
- ❌ 不做独立孤岛式"发票识别工具站"，识别能力内嵌于录入 + 发票箱。
- ❌ P0 不做完整税务局查验 API 对接（留 P1 轻量版）。
